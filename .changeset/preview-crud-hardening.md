Keep track of every Slack app the preview flow creates, found by running `vercel-slack build` against Slack and Vercel:

- `SLACK_CLIENT_SECRET`, `SLACK_SIGNING_SECRET`, `SLACK_BOT_TOKEN`, `SLACK_APP_LEVEL_TOKEN` and `SLACK_USER_TOKEN` are saved as Sensitive environment variables, so Vercel never shows their values again.
- The CLI takes every secret it was given or received, and anything shaped like a Slack or Vercel token, out of all it prints: progress, warnings, errors and `--debug` output. `--debug` also redacts everything under keys like `api_access_tokens` and `credentials` whatever the names inside, a project's deploy hook URLs, and credentials in headers however they are passed, and shows nothing of a secret shorter than 16 characters.
- `--cleanup` deletes a stale branch's variables only once its app is deleted or Slack says it's gone, and `SLACK_APP_ID` last. It used to delete them when Slack couldn't be reached or refused, which left an app nothing could find again. It also recognises an app that was already deleted, which Slack answers with `no_permission`, and says what to do about an app Slack keeps refusing to delete.
- `vercel-slack build` and `preview` save an app's tokens on any run that installs it, not only the run that created it, so a branch whose first install didn't go through gets its `SLACK_BOT_TOKEN` once it does. The CLI then replaces the deployment, as it does for a new app, and a deployment it started doesn't start another.
- When Vercel doesn't save a new app's credentials, the app is deleted again, so the next build doesn't create a second one next to it.
- When Slack rejects the manifest while updating a branch's app, the build fails with Slack's problems, where it created a second app.
- When Slack doesn't install the app, the build prints Slack's error code, like `service_limits_exceeded` for a workspace that has reached its app limit, where it said "Unknown error". `PreviewResult.installError` has the code. The build no longer prints an install URL for an app it installed, and says why a branch that had an app gets a new one.
- Branch names with characters Slack rejects in an app name, like `+`, `@`, `#` or accented letters, no longer fail the build.
- A build that starts with an expired configuration token uses the one another build already rotated, where it rotated again with a refresh token that was already used. Rotated tokens are saved to the environments, and with the type, the old ones had, where they were copied to every environment. The token isn't rotated when Slack couldn't be reached to check it.
- A manifest that isn't valid JSON or YAML, or has no `display_information.name`, fails before anything is created, with the file's path. An empty `MANIFEST_PATH` means `manifest.json`.
- README: the example manifest is one Slack accepts, and the version flag is `-V`.
- What `vercel-slack build` prints is rewritten to say what happened and what to do, in a line or two each. Failures are marked `✗` like `✓` and `⚠`. A build that doesn't install the app says where to install it by hand, on every build and not only the one that created the app. The build says the deployment it cancels is replaced by the new one, since Vercel shows it as Canceled. A skipped build says why. Vercel's errors show as their code and message, not raw JSON. The service token is no longer checked before the install, which reported an invalid one twice.
- A token with a line break, space or non-ASCII character inside it, like one copied across a wrapped line, is refused by name before any request. It used to be reported as Slack being unreachable, with an error that printed part of the token. Space around a token is dropped. `--cleanup` also keeps a branch's variables when its `SLACK_APP_ID` has no readable value, and `vercel-slack build` checks the Vercel token, branch and manifest before it rotates the configuration token. `HTTPError.body` has secrets taken out, like the error's message.
